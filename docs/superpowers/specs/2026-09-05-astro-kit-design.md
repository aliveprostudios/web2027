# Astro Kit: a reusable starter extracted from the Alive ProStudios site

**Date:** 2026-09-05
**Status:** Approved in conversation by Javad Ahmadi, 2026-09-05
**Owner:** Alive ProStudios Inc.

## 1. Purpose

Alive ProStudios builds client websites. Every build today starts from scratch,
even though the design, the style guide, the component set, the build scripts
and the engineering rules are settled. The kit turns that settled work into a
GitHub template repository so that a new project consists only of intake:
brand, sitemap and content. The code is versioned once and improved for every
client at the same time.

The kit is extracted from this repository. This repository is not changed by
the extraction.

## 2. Decisions

Settled in the brainstorming session on 2026-09-05. Do not reopen without
asking Javad.

1. **Site shape is fixed.** The kit builds service-business sites with Alive's
   shape: home, service groups, about, work, case studies, blog, questions,
   contact, legal. Section names, URLs and counts vary; the set of section
   kinds does not. Product catalogues and e-commerce are out.
2. **Per client, the design changes colours, logo and fonts.** Type scale,
   grid, spacing, radii, motion and every component stay as Design System C
   specifies them.
3. **The kit is a GitHub template repository**, `aliveprostudios/astro-kit`.
   A new project starts with "Use this template". No local master folder, no
   scaffolder command.
4. **The kit ships a fictional sample client**, one page per section, marked
   so it cannot reach production.
5. **Staging is hosted on Alive's Cloudflare account.** Production is decided
   per client after approval: Alive-hosted or client-hosted. The kit is
   host-agnostic because `dist/` is plain files.
6. **The home page is five blocks:** hero, intro, services, work, closing.
   Each is content-driven.
7. **Intake is files.** `intake/brand.md` and `intake/sitemap.md`, read by a
   kickoff skill. Conversational intake can be layered on later and must
   produce the same two files.
8. **Engineering rules travel with the kit. Editorial rules are settings.**
   Language variant, banned words, the no-pricing rule and the no-em-dash rule
   live in `content/site.md`, defaulted to Alive's values.
9. **The Alive site stays as it is for now.** The kit is extracted from it and
   diverges. After one client site has shipped on the kit, migrating Alive's
   own site onto it is a separate spec.

## 4. Where the brand lives

Everything that changes per client lives in exactly three places. A client
project never edits `src/` for branding.

### 4.1 `content/site.md`

Read through a `site` collection with a schema, so a missing required field
fails the build. Fields:

| Field | Required | Notes |
|---|---|---|
| `name` | yes | Display name, used in nav, footer, Organization schema |
| `legalName` | yes | Footer and schema |
| `tagline` | no | |
| `domain` | yes | Production origin, also written to `astro.config.mjs` by kickoff |
| `founded` | no | |
| `location` | yes | city, region, country |
| `address` | no | Postal address for schema |
| `phone` | no | |
| `email` | yes | |
| `sameAs` | no | Array of social and profile URLs, feeds Organization `sameAs` |
| `areaServed` | no | Array of countries or regions |
| `gtmId` | no | Google Tag Manager container. Absent means no GTM markup is emitted |
| `formEndpoint` | no | Contact form POST target. Absent means the contact page renders without a form and says so at build time with a warning |
| `fontsHref` | no | One stylesheet URL for the fonts, replaces the hard-coded Google Fonts link in `BaseLayout.astro`. Absent means system fonts |
| `editorial.language` | yes | BCP 47 tag, default `en-CA` |
| `editorial.bannedWords` | yes | Array, default `["honest", "honestly"]` |
| `editorial.noPricing` | yes | Boolean, default `true` |
| `editorial.noEmDash` | yes | Boolean, default `true` |
| `sample` | yes | Boolean. `true` in the kit, must be `false` before production |

### 4.2 `src/styles/tokens.css`

A brand block at the top of the file, and nothing brand-specific below it.
Tokens are renamed from colours to roles so a client whose accent is blue is
not editing a variable called orange:

| Today | Kit | Role |
|---|---|---|
| `--brand-orange` | `--brand-accent` | CTAs, dots, highlights, hover, small accent text |
| `--brand-lime` | `--brand-secondary` | H2 colour, dark-button hover |
| `--brand-forest` | `--brand-tertiary` | Supporting colour |
| `--brand-mist` | `--brand-neutral` | Light lines and surfaces |
| `--brand-black` | `--brand-dark` | Footer, dark surfaces base |

Font slots keep their names: `--font-sans`, `--font-condensed`, `--font-mono`.
The three derived values that reference a brand colour, `--rail-pulse-orange`,
`--focus-ring` and the theme comment block, are rewritten against the roles.
The rail token is renamed `--rail-pulse-accent`.

Everything below the brand block, including the grey surface family, the
gutter, the z-index scale and the motion tokens, is Design System C and is not
a per-client setting.

### 4.3 `content/assets/brand/`

Fixed file names, so no component changes when a logo does:

- `logo.svg` and `logo-white.svg`
- `icon.svg`
- `og-image.jpg` at 1200x630
- `favicon.svg`, `favicon-32.png`, `apple-touch-icon.png`

Kickoff copies these from the paths named in `intake/brand.md`. The build
fails if any is missing.

## 5. Sections and routes

The section list is derived from `content/landing/`, replacing the constant in
`src/lib/sections.ts` and the hard-coded About entry in `src/lib/nav.ts`.

Each landing file carries:

| Field | Notes |
|---|---|
| `title` | Menu label and landing H1 |
| `url` | Section base path. `/work/case-studies` and `/common-questions` are the kit defaults, not code |
| `order` | Menu position |
| `kind` | One of `pillar`, `work`, `case-studies`, `blog`, `questions`, `contact`, `legal` |
| `stage` | Boolean, `pillar` only. `true` numbers the section as a stage, as the service groups are today; `false` leaves it plain, as About is today |

A `pillar` section is any landing file of that kind with a matching folder
`content/<section>/`. Service groups and About are both pillars, so the
separate `alive-pro/` route is retired and `src/pages/[section]/` serves them
all. Related Services for a pillar lists its siblings, which is what both
routes do today.

The other kinds keep their existing routes, with the base path read from the
landing file instead of the folder name.

**Empty section rule.** A section whose content folder holds no published page
is dropped from the menu, the landing rows, every count, the sitemap and the
routes, with no code change and no error. A landing file with no children
logs one build warning naming the file. This is rule 1 of the Alive site
applied to whole sections.

Service group membership comes from the folder, `content/<group>/<page>.md`,
so the `category` enum on the services collection is removed.

## 6. Home page

Five blocks, all from `content/home/`:

1. **Hero.** H1 with optional `heroLines`, caption, hero image or video.
2. **Intro.** Heading, prose, one link.
3. **Services.** One row per pillar section that has `stage: true`, in order,
   with the blurb from its landing file.
4. **Work.** Case study tiles from `caseStudies` in frontmatter, defaulting to
   the first three by `order`. Absent when there are no case studies.
5. **Closing.** The closing statement and Next Step.

The clients logo wall, the reel, the framework diagram, the gallery, the
founder quote and the feature image are not in the kit. They stay on the Alive
site.

## 7. Intake

`intake/` is outside `content/` so nothing in it can ship by accident.

### 7.1 `intake/brand.md`

Every field in section 4.1, each with a one-line comment, plus:

- the five colours, as hex
- the three font families and the `fontsHref`
- the paths of the six brand asset files
- the Cloudflare worker name for staging

### 7.2 `intake/sitemap.md`

- A sections table: kind, title, URL, order, include yes or no.
- A pages list per section: title and slug.
- A redirects table from the client's old site: from, to. Written to
  `SITEMAP.md`, which `postbuild.mjs` already reads.
- The production domain.

### 7.3 Sample client

The kit ships as **Sample Industrial Inc.**, domain `sample.example`, a
fictional manufacturer, with one page per section written in the real page
shape so every slot is demonstrated. Every sample page carries `sample: true`
in frontmatter and `content/site.md` carries `sample: true`.

## 8. The kickoff skill

`alive-kit-start`, in `.claude/skills/` inside the kit so it travels with the
template. One pass:

1. Read `intake/brand.md` and `intake/sitemap.md`. Stop, listing the fields,
   if any required field is empty.
2. Write `content/site.md`, the brand block in `tokens.css`, `SITEMAP.md`,
   the landing files with titles and URLs, `astro.config.mjs` site, and the
   worker names in `wrangler.jsonc`.
3. Copy the brand assets into `content/assets/brand/`.
4. Run `npm run build` and report the result: route count, redirect count,
   and any warning.

Kickoff is idempotent: running it again after editing intake rewrites the same
files and touches nothing else.

## 9. Guards

Two scripts, both run inside `npm run build` the way `blog-check.mjs` is today.

**`sample-guard.mjs`.** Fails a production build while any page carries
`sample: true` or `content/site.md` carries `sample: true`, listing the files.
A staging build (`STAGING=1`) passes with a warning, so a half-replaced site
can be previewed.

**`content-check.mjs`.** Reads `editorial` from `content/site.md` and checks
every Markdown file under `content/`:

- em dashes, when `noEmDash` is true: fail
- banned words, whole-word and case-insensitive: fail
- a currency amount or a percentage, when `noPricing` is true: warning with
  file and line, because legitimate figures exist

## 10. Rules by home

| Rule | Home | Travels to client sites |
|---|---|---|
| Content is the source of truth, no hard-coded lists | `CLAUDE.md` | yes |
| One H1, no skipped levels, every redirect shipped, CSP hashed | `CLAUDE.md` | yes |
| The traps list | `CLAUDE.md` | yes, minus the Alive-specific entries |
| Canadian English, banned words, no pricing, no em dash | `content/site.md` | as defaults, editable |
| Type scale, grid, components, motion | `docs/design-system-c.html` | yes, as the binding grammar |
| Alive's colours and fonts | nowhere in the kit | no |

The design system document keeps Alive's colours. It is the reference for
grammar; the tokens are what a client site renders. Making the document
re-colour itself from tokens is out of scope.

## 11. The process: `KIT.md`

One page at the repo root, eight steps, each with its command and its
done-check.

1. **Start.** "Use this template" on GitHub, repo named `<client>-site`.
   Clone.
2. **Intake.** Fill `intake/brand.md` and `intake/sitemap.md`, place the six
   brand asset files.
3. **Kickoff.** Run `alive-kit-start`. Done when the build is green with the
   client's name, colours and fonts on the sample pages.
4. **Content.** Replace sample pages with the client's Markdown. The blog uses
   `blog-writer` and a publish skill generalized from
   `alivepro-blog-publish`. Done when `sample-guard` passes without
   `STAGING=1`.
5. **Verify.** `npm run build`, `npm run check`. Preview through
   `npm run preview` (wrangler), never `astro dev`, so headers and redirects
   are exercised.
6. **Staging.** Push `staging`. Deploys to `staging-<client>` on Alive's
   Cloudflare account, `X-Robots-Tag: noindex`.
7. **Audit.** Run `CHECKLIST.md` from `astro-skill-javad` against the served
   staging site. That skill's phases 2 to 6, 8 and 9 are done by the kit;
   phases 7, 10, 11 and 12 remain per project.
8. **Production.** Alive-hosted: push `main` to a second Worker with the
   client's domain as a Custom Domain. Client-hosted: the client connects
   their Cloudflare account to the repo with the same build command and
   output directory, and Alive's staging Worker is retired. Both paths are
   written out with their exact steps.

## 12. Testing

All runnable in the kit repository alone, in `.github/workflows/kit.yml` on
every push.

- **Build test.** `npm run build` with `STAGING=1` on the sample client
  passes.
- **Rebrand test.** Run kickoff against `intake/fixtures/brand-b.md`, build,
  then assert that `dist/` contains none of a fixed list of strings: every
  Alive value (`Alive`, `aliveprostudios`, `Javad`, `#F76E1E`, `#95C83F`,
  `Barlow`, `GTM-PJLQRZC`, `mwlejogn`) and every Sample Industrial value.
  This is the test that catches a hard-coded string left behind during
  extraction.
- **Empty-section test.** Move one section's content folder aside, build,
  assert its routes, menu entry, landing row, count and sitemap entries are
  gone and the build emitted exactly one warning naming the landing file.
- **Guard tests.** A production build with a sample page fails. A production
  build with `sample: false` everywhere but one em dash in a page fails. A
  page with a banned word fails.

## 13. Extraction order

The Alive repository is read, never written, during extraction.

1. Create `astro-kit` from a copy of this repository. Remove Alive's content,
   assets, the `intake/` drafts, `LAUNCH.md`, `TASKS.md`, `dashboard.html` and the
   Alive-specific entries in `CLAUDE.md`. Add the sample client. Build green.
2. Rename tokens to roles and move every identity value into
   `content/site.md`, file by file across the 35 files in `src/` that carry
   one today. The rebrand test is the finish line for this step.
3. Generalize sections: derive the list from landing files, retire the
   `alive-pro/` route, remove the services `category` enum, add the empty
   section rule.
4. Reduce the home route to the five blocks.
5. Write `sample-guard.mjs`, `content-check.mjs`, the intake templates, the
   kickoff skill, the blog publish skill generalized from
   `alivepro-blog-publish`, `KIT.md`, the workflow file and the rebrand
   fixture.
6. Ship one client site on the kit. Then write the Alive migration spec.

## 14. Out of scope

- The `npm create alive-site` scaffolder.
- Conversational intake.
- Migrating the Alive site onto the kit.
- A design-system document that re-colours itself from tokens.
- Self-hosted fonts.
- i18n beyond what the Alive site already carries.
- The clients logo wall, reel, framework diagram, gallery, founder quote and
  feature image blocks on the home page.
